## Known limitations

- **Signing out closes every session of that account** (SEC-01), including those of another gatehouse using the same account. It is the cost of revoking without storing each session in the database; with one account per guard it has no effect.
- **The PostgreSQL superuser still exists** inside the database container: only migrations use it (ADR 0012). Do not publish the database port in production.
- **No inactivity timeout (SEC-09, accepted risk, ADR 0014).** The session lasts a fixed 12-hour shift. The gatehouse screen refreshes itself every 10 s, so the server cannot tell an idle gatehouse from an attended one; signing out at shift change is part of the procedure.
- **The common-password list is short and local (SEC-08).** It does not query breached-password databases on the Internet; the 12-character minimum does most of the work.
- **Rate limiting, the per-email lockout and the alert live in each instance's memory.** They reset with the API and, with several replicas, each counts separately; horizontal scaling would need a shared store (for example Redis).
- **The per-email lockout can be triggered on purpose:** someone who knows a guard's email can keep them from signing in for 15 minutes. It is logged (`auth.account_locked`) and expires on its own (ADR 0013).
- **Account changes from the terminal (`npm run users`) are not in the app's audit log,** because no app user makes them (ADR 0008). They remain in the server's terminal history.

## When deploying

1. Always serve over **HTTPS** and set `TRUST_PROXY=true` if there is a proxy in front (needed for the `Secure` cookie and the real IP).
2. Generate a random `JWT_SECRET` (≥ 32 characters) and a strong PostgreSQL password. Changing `JWT_SECRET` closes every session.
3. Create the first administrator with `npm run create-admin` on the server and do not reuse passwords.
4. Generate **all** production secrets fresh (do not reuse the development ones or store them in synced folders such as OneDrive), use different generated passwords for `POSTGRES_PASSWORD` (table owner) and `APP_DB_PASSWORD` (API user), and apply migrations with `npm run db:deploy` (the `migrate` service), never with the API user.
5. Set up database backups.
6. Do not run the demo seed, `demo:setup` or `e2e:prepare` (all three refuse to run in production), and do not expose the PostgreSQL port to the Internet.
7. Set up a monitoring alert on the `security.alert` and `auth.account_locked` log events (ADR 0013).
